# AIレビュー判定基準

## 1. 目的

この文書は、Tech-Quest における AI 一次レビューの判定基準を明確化するための基準書です。  
AI レビューは最終合否を決めるものではなく、受講生への改善フィードバックと、メンターの一次確認を支援するための参考情報として扱います。

## 2. 前提

- AIレビューは `参考情報`
- 最終判定は `mentor`
- AI は `合格 / 差し戻し` を決めない
- AI は `README / モック画像 / コード証跡` をもとに、厳しめに評価する

## 3. 評価観点

AI は次の 3 観点で 0 から 5 点を付けます。

### セキュリティ

- API キーや機密情報の露出がないか
- 外部連携時の危険な実装がないか
- 入力値や例外処理が最低限考慮されているか

### 可読性

- README と提出物から実装意図が追えるか
- 命名、関数分割、コメントが最低限整理されているか
- ハードコーディングや属人的な実装が強すぎないか

### ビジネス価値

- 課題の業務課題に対して解決筋が合っているか
- 工数削減、ミス削減、見落とし防止などの価値が説明されているか
- 導入後の状態が具体的にイメージできるか

## 4. スコア基準

### 5 点

- 要件根拠が十分で、重大な懸念がほぼない
- README、モック画像、コード証跡の整合が取れている
- メンターが最終確認しやすい完成度

### 4 点

- 大枠は非常に良い
- 軽微な補足不足や改善余地はあるが、重大な欠落はない

### 3 点

- 方向性は正しい
- ただし README の根拠不足、実装説明不足、業務価値の弱さなどが残る
- 追加確認や軽い修正が必要

### 2 点

- 不足が複数ある
- 要件の一部未達、説明不足、品質懸念があり、再修正が必要

### 1 点

- 重大な不足や危険がある
- そのままではレビュー通過候補として弱い

### 0 点

- 提出物からほとんど評価できない
- README、モック画像、コード証跡のいずれも根拠として不足している

## 5. 厳しめ評価ルール

以下に該当する場合、AI は高得点を付けません。

### 必須要件に `missing` がある

- `businessLogic` は `2 点以下`

### 高 severity のセキュリティ指摘がある

- `security` は `2 点以下`

### 可読性の中程度以上の指摘が複数ある

- `readability` は `2 点以下`

### 業務価値の説明が短い、または抽象的

- `businessLogic` は `2 点以下`

### コード証跡がない、または弱い

- `security` と `readability` は厳しめに抑える
- AI 結果には「本文ベースの暫定評価」である旨を残す

## 6. 合格条件チェックの扱い

AI は課題ごとに以下を `acceptanceChecks` として返します。

- 必須機能
- 最低限のエラーハンドリング
- 提出物要件

返却ステータスは次の 4 種です。

- `met`
  - 満たしている
- `partial`
  - 一部満たす
- `missing`
  - 不足
- `unclear`
  - 提出内容から断定できない

## 7. AI の見立てラベル

AI は点数とは別に、全体の見立てを 4 段階で返します。

- `strong`
  - メンター確認に進めやすい
- `borderline`
  - 追加確認が必要
- `needs_revision`
  - 修正推奨
- `major_revision`
  - 大幅修正推奨

このラベルはあくまでメンター補助です。  
最終的な合否判定はメンターが行います。

## 8. メンターが特に見るべきポイント

AI 結果を見るときは、次を優先して確認します。

- `missing` の acceptance check があるか
- high severity の指摘があるか
- `assessmentReason` に何が書かれているか
- `mentorFlags` に要確認事項が残っているか

## 9. 運用ルール

- AIレビュー未実行でも、緊急時はメンターがレビューしてよい
- ただし通常運用では AI レビュー結果を確認した上でレビューを進める
- AI の高評価だけで合格にしない
- AI の低評価でも、提出物の実態を確認してメンターが最終判断する
