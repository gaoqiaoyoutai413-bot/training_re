# AI 一次レビューのプロンプト設計

## 1. 役割定義

Gemini の役割は「合否判定の自動化」ではなく、「受講生への即時フィードバック生成」と「メンターのレビュー補助」です。ここを曖昧にすると、AI の誤判定が運用リスクになります。

## 2. 精度向上の基本方針

### 採点は甘くしない

- 4 点以上は「根拠が十分で重大な懸念が少ない」場合だけ付ける
- 必須要件に `missing` があれば高得点を付けない
- 高 severity の指摘がある観点は 2 点以下を基本にする
- 業務価値の説明が抽象的で、工数削減や運用改善の根拠が弱い場合は 3 点以下に抑える
- AI の見立ては参考情報であり、最終判定はメンターが行う

### プロンプトは 1 本に詰め込まない

- セキュリティ
- 可読性/保守性
- ビジネス価値の妥当性

この 3 観点を別セクションで明示し、出力スキーマも固定します。

### 入力を構造化する

AI に渡す内容は自然文の寄せ集めではなく、以下の JSON 形を推奨します。

```json
{
  "task": {
    "title": "課題名",
    "description": "課題本文",
    "expectedBusinessOutcome": "期待する業務効果"
  },
  "submission": {
    "sourceCodeUrl": "https://...",
    "businessValueText": "受講生の考察",
    "evidenceSummary": [
      "画面キャプチャ",
      "PDF 設計書"
    ]
  },
  "reviewPolicy": {
    "focus": ["security", "readability", "business_logic"],
    "forbidden": ["final_pass_fail_decision"]
  }
}
```

### 出力は JSON Schema に制限する

自由文中心だと後続の UI 表示や分析に不向きです。以下のような固定スキーマが有効です。

```json
{
  "overallAssessment": "strong|borderline|needs_revision|major_revision",
  "assessmentReason": "string",
  "summary": "string",
  "scores": {
    "security": 0,
    "readability": 0,
    "businessLogic": 0
  },
  "findings": [
    {
      "severity": "high|medium|low",
      "category": "security|readability|business_logic",
      "title": "string",
      "detail": "string",
      "suggestion": "string"
    }
  ],
  "mentorFlags": [
    "string"
  ]
}
```

## 3. 推奨システムプロンプト

```text
あなたは IT コンサル新人研修プラットフォームの一次レビュー AI です。
目的は、提出物に対して受講生が次に改善すべき点を明確に伝え、メンターのレビュー負荷を下げることです。

必須ルール:
1. 最終的な合否判定はしない
2. セキュリティ、可読性、ビジネス価値の3観点で評価する
3. 根拠が弱い場合は断定せず「要確認」と記載する
4. 4点以上は明確な根拠がある場合だけ付け、甘い採点をしない
5. 出力は指定された JSON のみ
6. 指摘は改善可能な具体策を含める
7. 提出者を否定せず、建設的で簡潔な表現を使う
```

## 4. 推奨ユーザープロンプト

```text
以下の課題情報と提出内容をレビューしてください。

- 課題の目的から逸脱していないか
- コードや構成に重大なセキュリティ懸念がないか
- 可読性・保守性に改善余地がないか
- ビジネス価値の説明に定量性・妥当性があるか
- 4 点以上は「根拠が十分で大きな懸念が少ない」場合に限定する

断定できない点は mentorFlags に要確認事項として残してください。
```

## 5. 精度向上テクニック

### 課題ごとの観点差分を持つ

課題 1 と課題 10 では見るべき観点が異なります。課題マスタに以下を持たせると有効です。

- `review_rubric_json`
- `expected_artifacts_json`
- `common_failure_patterns_json`

これを毎回 AI に渡すことで、課題ごとの評価軸がぶれにくくなります。

### Few-shot を課題カテゴリ単位で入れる

- 自動化課題の良いレビュー例
- AI 活用課題の曖昧なレビュー例と改善例
- 外部連携課題のセキュリティ観点例

カテゴリごとに 1 から 2 例を入れるだけでも安定しやすいです。

### 受講生向け文面とメンター向け文面を分ける

1 回の推論で両者向けを生成してもよいですが、出力フィールドは分離します。

- `studentFeedback`
- `mentorFlags`

## 6. 運用上の注意

- ソースコード URL の取得失敗時はレビューを中断し、エラー理由を保存
- 長大なリポジトリは全件読ませず、対象ディレクトリや主要ファイルに絞る
- プロンプトバージョンを DB 保存し、精度比較可能にする
- メンターの再評価結果と比較し、AI 指摘の正答率を継続計測する

## 7. 精度改善の KPI

- AI 指摘のうちメンターが有効と判断した割合
- AI が見逃した重大指摘の件数
- 受講生の再提出までの平均時間短縮
- メンター 1 件あたりレビュー時間の削減率
