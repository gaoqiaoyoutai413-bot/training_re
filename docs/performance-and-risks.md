# パフォーマンス懸念点と提案

## 1. 結論

月間30名、年間360名超の規模自体は Supabase + Next.js 構成で十分に扱えます。懸念は純粋なレコード件数よりも、提出物ファイル、AI レビュー非同期処理、運営向け集計クエリ、ナレッジ公開時の権限制御に集中します。

## 2. 主な懸念点

### 集計クエリの肥大化

バッチ別進捗率、平均クリア時間、スキルスコアを毎回オンザフライで算出すると、画面表示ごとに複雑な集計が走ります。

対策:

- `student_progress_view`
- `batch_metrics_view`
- `student_skill_scores_view`

を用意し、必要に応じて Materialized View 化します。

### AI レビューのスパイク

提出締切直前にレビュー要求が集中すると、Gemini API のレイテンシと失敗率が UX に影響します。

対策:

- 同期レビューを避け、ジョブキュー方式にする
- 再試行ポリシーを持つ
- 提出直後は「受付済み」を即返す
- AI 失敗時もメンター導線を止めない

### ファイル保管コストと一覧性能

PDF や画像が増えると、DB ではなく Storage のメタデータ設計が重要になります。

対策:

- DB には最小メタ情報のみ保持
- サムネイルやプレビュー URL は必要時生成
- 一覧画面で重量ファイルを都度ロードしない

### RLS と複雑な JOIN

RLS は強力ですが、複雑な条件と多段 JOIN が増えると性能劣化の原因になります。

対策:

- ポリシー判定に必要なキーへインデックスを付与
- 一覧系は必要列を絞った View を使う
- 認可ロジックをテーブル設計段階から単純化する

## 3. 将来の拡張を見据えた提案

### 課題追加

課題 11 以降を追加しやすくするため、課題依存関係や評価ルーブリックは全て DB 管理にします。

### マルチバッチ運用

年間で複数バッチが並行する場合、`batch_members` を基点に集計を行い、ユーザーが複数バッチをまたげる設計にしておくと柔軟です。

### ナレッジ資産化

優秀解答ライブラリは将来的に検索ニーズが高まるため、以下の追加を見据えるとよいです。

- タグ
- 課題別ハイライト
- 全文検索
- 類似課題レコメンド

## 4. 実装時のボトルネック回避策

- `submissions` と `mentor_reviews` は更新頻度が高いため、不要なトリガーを増やしすぎない
- ダッシュボードは SSR 初回描画 + 軽量再検証で安定化
- リアルタイム更新はレビュー進行など必要箇所に限定
- Storage と Drive の二重保存は非同期化

## 5. 推奨監視項目

- AI ジョブ待ち時間
- AI レビュー失敗率
- バッチ別レビュー滞留件数
- ダッシュボード主要 API の p95 レイテンシ
- Storage 容量増加率

## 6. 優先度付き提案

1. 最初から集計 View を分ける
2. AI レビューを非同期ジョブとして設計する
3. RLS 前提でインデックスを設計する
4. 課題・レビュー基準を DB マスタ化する
5. ナレッジ共有は合格後の明示公開フローに限定する
