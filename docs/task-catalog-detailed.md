# 課題一覧 詳細版

この文書は、Tech-Quest で現在公開している 10 課題を、`背景・導入前の状況`、`解決したい具体的な課題`、`最終解決（ゴール）`、`提出物`、`評価観点` まで含めて一覧化したものです。

## 1. スプレッドシートのデータを利用した「見積書自動作成」

### 背景・導入前の状況

別システムから抽出した実績データをスプレッドシートにまとめ、そこから毎回目視で必要な項目を拾い出して、手作業で見積書に転記しています。部署や営業担当ごとにテンプレートが異なり、新人がどう書けばよいか迷いやすい状態です。

### 解決したい具体的な課題

- 目視による転記作業に時間がかかる
- 忙しいと見積書の作成そのものが滞る
- 手作業による入力ミスが起きやすい

### 最終解決（ゴール）

出勤実績や顧客情報から、ボタンひとつで統一フォーマットの見積書が自動生成される状態を目指します。人間は確認だけに集中し、数時間かかっていた作業を数分に短縮します。

### 学習テーマ

- GAS によるシート操作
- スプレッドシートのデータ抽出
- フォーマット転記
- PDF 出力

### 提出物

- README
- モック画像または生成見積書の画面キャプチャ
- 補足リンク任意

### 代表的な評価観点

- カスタムメニューから実行できるか
- 顧客名や金額の未入力時に適切に止められるか
- 見積書フォーマットが統一されているか

## 2. カレンダー情報を取得する「会議候補日抽出ツール」

### 背景・導入前の状況

複数人で会議を行うたびに、該当メンバーの Google カレンダーを一つひとつ開き、それぞれの予定を見比べながら空き時間を探しています。

### 解決したい具体的な課題

- カレンダーを行き来する前準備に無駄な時間がかかる
- 日程調整のたびに同じ確認作業が発生する
- 候補日時の洗い出しが属人的になる

### 最終解決（ゴール）

指定メンバーのカレンダー情報を自動で参照し、全員が空いている会議候補日を瞬時にリストアップできる状態を目指します。

### 学習テーマ

- Google Calendar 連携
- 日時比較
- 配列・ループ処理
- 候補時間帯抽出ロジック

### 提出物

- README
- 候補日一覧のモック画像
- 補足リンク任意

### 代表的な評価観点

- 直近 1 週間など検索期間を適切に絞れているか
- 複数メンバーの空き時間比較ができているか
- 人が見て分かりやすい時間表記になっているか

## 3. 条件に応じた「Slack・チャットツールアラート通知システム」

### 背景・導入前の状況

顧客への追客状況やイベントスタッフの起床・出発報告などをスプレッドシートで管理しています。管理者がシートに張り付いて監視しないと、未報告や放置案件に気づけません。

### 解決したい具体的な課題

- 目視確認の労力が大きい
- 放置案件や未報告を見逃しやすい
- 追客漏れで失注するリスクがある

### 最終解決（ゴール）

システムがスプレッドシートを自動監視し、条件に該当するものだけ Slack などへ通知する状態を目指します。管理者が見張り続ける必要をなくし、取りこぼしを減らします。

### 学習テーマ

- Webhook 連携
- 定期実行トリガー
- 条件分岐
- JSON ペイロード作成

### 提出物

- README
- 通知が送られたチャット画面のモック画像
- 補足リンク任意

### 代表的な評価観点

- 通知対象が 0 件のときは送信しないか
- Webhook URL を安全に扱えているか
- 誰が何をいつまでに対応すべきか分かる通知文になっているか

## 4. メッセージングAPIを使った「LINEリマインダーボット」

### 背景・導入前の状況

往診日やシフト、請求書などの案内を、担当者がスプレッドシートを見ながら各個人の LINE 宛に手作業で一件ずつ送信しています。

### 解決したい具体的な課題

- 送信対象が多いと毎日数時間を取られる
- 送信漏れのリスクが高い
- 連絡作業のせいで他業務が圧迫される

### 最終解決（ゴール）

システムが対象者を抽出し、予定の 7 日前や前日に個別 LINE へ自動送信する状態を目指します。送信作業を短縮し、送信漏れを減らします。

### 学習テーマ

- LINE Messaging API
- Push 通知
- スケジュール判定
- API エラーハンドリング

### 提出物

- README
- LINE 受信モック画像
- 補足リンク任意

### 代表的な評価観点

- アクセストークンを安全に扱えているか
- 日付計算とタイムゾーンに配慮できているか
- 個別送信のエラーを適切に処理できるか

## 5. 生成AIを利用した「募集要項・テキスト整形ツール」

### 背景・導入前の状況

クライアントから届く依頼文がメールや LINE など多様な形式でばらばらです。その内容を手作業で社内統一フォーマットに整形し直す作業に大きな工数がかかっています。

### 解決したい具体的な課題

- コピペと転記の工数が大きい
- フォーマット揺れによって品質が安定しない
- 同じような整形作業が繰り返される

### 最終解決（ゴール）

どのような形式の依頼文でも、AI が内容を読み取って社内規定のフォーマットに変換し、数分で処理できる状態を目指します。

### 学習テーマ

- LLM API 呼び出し
- プロンプト設計
- JSON 構造化
- 例外処理

### 提出物

- README
- 整形前後のモック画像
- 補足リンク任意

### 代表的な評価観点

- 出力フォーマットを安定させるプロンプトになっているか
- JSON パースエラーに対応しているか
- AI キーを安全に扱っているか

## 8. 画像認識（OCR）を用いた「領収書・請求書転記システム」

### 背景・導入前の状況

日々届く請求書や紙の領収書を、経理や事務担当者が目視で確認し、金額や日付を手入力しています。

### 解決したい具体的な課題

- ダウンロード、格納、転記の単純作業が多い
- 手入力ミスが起きやすい
- 最新データの反映に遅れが出る

### 最終解決（ゴール）

請求書や領収書を所定フォルダへ置くだけで、OCR により必要情報を抽出し、管理用シートへ自動転記される状態を目指します。

### 学習テーマ

- OCR
- 正規表現
- 画像からのデータ抽出
- フェイルセーフ設計

### 提出物

- README
- OCR 結果のモック画像
- 補足リンク任意

### 代表的な評価観点

- 金額や日付の表記揺れに対応できているか
- 読み取り失敗時に手動確認フラグを立てられるか
- 人による最終確認を前提にした運用になっているか

## 10. GAS Webアプリ機能を用いた「日報・業務報告フォーム」

### 背景・導入前の状況

現場からの日報や進捗報告が、紙、メール、LINE など店舗や人によってばらばらな形式で送られてきます。

### 解決したい具体的な課題

- 管理者が一つのデータベースへ手動転記している
- 報告漏れや不備の確認に手間がかかる
- リアルタイム性が低い

### 最終解決（ゴール）

自社専用の報告用 Web アプリに入力方法を統一し、送信データが自動で蓄積される状態を目指します。転記作業をなくし、リアルタイムで状況把握できるようにします。

### 学習テーマ

- GAS Web アプリ
- HTML / CSS / JavaScript
- `google.script.run`
- 入力バリデーション

### 提出物

- README
- フォーム画面のモック画像
- 補足リンク任意

### 代表的な評価観点

- スマホでも入力しやすいか
- フロントとバックエンドの連携ができているか
- 送信重複や未入力を適切に防げているか
